Why I built it

StackGraph is three things at once: a portfolio project, a learning project, and a tool I wanted for myself.

After finishing my training at the Developer Akademie, I wanted a project that is entirely my own, not a course assignment and not a tutorial clone. I use Docker Compose a lot in my own setups, and I kept running into the same problem: the longer a compose file gets, the harder it is to see what is going on. Which service depends on the database, which ones share a network, where data is persisted. The answers are all in the file, but spread across dozens of indented lines. A graph shows them at a glance, and that became the idea for StackGraph.

The learning side was just as deliberate. "Parser" was a word I had used many times without really knowing what it involves, so I wanted to find out by building the part that matters here myself. js-yaml reads the YAML syntax. Everything after that is my own code: turning an untyped tree into a validated, typed model, and turning every problem into an error message a person can act on. It was also the first time I designed an architecture before writing feature code, instead of letting the structure grow as I went. The rest of this page is about the decisions that came out of that.

Goals & constraints

Five requirements shaped almost every technical decision in StackGraph, and each of them ruled something out.

Compose files often contain internal hostnames, registry paths and sometimes credentials in environment variables. StackGraph therefore has no backend, no upload and no analytics, and even the fonts are self-hosted so that no request goes to a third party. Parsing, layout and rendering all run on the user's machine, which means every dependency has to justify its weight in the bundle. The graph follows the editor without a render button. Half-typed YAML is invalid more often than it is valid, so the graph must not vanish on every keystroke, and a slow layout run must never overwrite the result of a newer one. "Invalid YAML" does not help in an 80-line file. Every error names its cause, gives the line and column or the path in the file, and for common mistakes a hint on how to fix it. Dependencies in a compose file usually form layers, from the proxy down to the database. The layout has to make that order visible, and the result has to leave the app as a clean SVG file. That ruled out force-directed layouts, which are good at clusters but say nothing about direction. It also meant owning the SVG markup instead of handing it to a graph library. A graph is visual by nature, so everything it shows also needs a route that works with a keyboard and a screen reader, and no information may depend on color alone.

Just as deliberate is what v1 leaves out. File upload, drag and drop and PNG export are planned, but none of them was needed to prove the core idea.

How it works

Every edit runs through the same short pipeline: wait for a pause, parse, lay out, draw. Each step hands a typed result to the next.

  1. 01

    Wait for a pause

    The editor writes into a single signal. StackGraph waits until typing has paused for 300 ms before doing any work, and each new keystroke drops whatever is still pending. A layout that finishes late is simply ignored, so it can never replace a newer one.

  2. 02

    Parse into a typed model

    js-yaml turns the text into a plain JavaScript tree. parseCompose then checks that tree and converts it into a ComposeModel. Short and long notations end up in one shape, so "8080:80" and "443" both become port mappings, and structural problems are collected across the whole file instead of stopping at the first one. The result is either a valid model or a list of errors, never something in between. The idea behind this is known as "parse, don't validate".

  3. 03

    Compute the layout

    A pure function translates the model into the graph format of ELK, the Eclipse Layout Kernel. Services, networks and volumes become typed nodes; depends_on, network membership and volume use become three kinds of edges. Node sizes are calculated from their content before the layout runs, because ELK needs them to place anything. ELK's layered algorithm then arranges the graph top-down, so dependencies always point downwards. ELK is loaded only on first use and is not part of the initial download.

  4. 04

    Draw the graph

    Angular binds the positioned nodes and edges directly to SVG elements in a template, with no graph library between the data and the markup. d3-zoom only computes the pan and zoom transform; Angular applies it. Because the SVG on screen is StackGraph's own markup, exporting it means serializing exactly what is drawn, including its computed styles.

  5. 05

    Keep the last good graph

    While the input is invalid, the graph keeps showing the last valid state and the status bar explains what is wrong. An empty editor is treated differently: deleting everything is an intent, not an error, so the graph is cleared. If an update takes longer than 400 ms, a small "Updating…" indicator appears; shorter ones finish unnoticed.

Architecture

Four layers, and dependencies only point downwards. The core of StackGraph does not know that Angular components exist.

Model. At the bottom are plain TypeScript types: the ComposeModel the parser produces and the PositionedGraph the layout returns. compose.model.ts imports nothing at all. Every other part of the app agrees on these shapes, which makes them the real contract between the layers.

Pipeline. Above the model sit the steps described in How it works. Most of them are pure functions without Angular: parseCompose, the mapping to ELK, the node geometry, the reverse lookups behind "required by" and "used by", port formatting and error hints. Angular appears only where a browser or library API requires it. The Layout service wraps ELK's asynchronous API and its lazy loading, and the SVG export needs the DOM.

State. ComposeState is the only place that connects parser and layout. It owns everything that has to do with time: the pause before parsing, discarding outdated results, keeping the last valid graph. Components read its signals and never call the parser or the layout themselves.

Components. At the top, a single container, GraphPage, reads the state and holds the selection. Apart from Home and the editor, which write the text, the graph components receive their data through inputs and report back through outputs. The renderer only knows the PositionedGraph; the detail panel and the stack overview only know the ComposeModel. GraphPage connects the two through the service name. The graph and its text alternative are therefore two independent views of the same model, and neither is derived from the other.

What this buys. The parser, the mapping and the geometry are tested as plain functions, without a component or a DOM. Moving the layout into a Web Worker later only changes the inside of the Layout service, because its contract is a promise that stays the same. And the node geometry is defined once and used twice: the mapping uses it to tell ELK how large a node is, the shape components use it to draw that node. A node is always drawn exactly as large as ELK planned it.

What it costs. The positioned graph extends ELK's own types, and the renderer reads edge routes in ELK's format. Replacing ELK with another layout engine would therefore mean touching the renderer too. A neutral graph type would remove that coupling, but with a single layout engine it would add a translation step that nothing currently needs.

Key decisions

Four decisions shaped StackGraph more than any others. Each card names what it follows from, the options, and the price.

Options. ngx-graph, a maintained Angular graph component with dagre layout; D3, whose built-in layouts are force-directed or made for trees; or ELK for positions only, with the drawing done in Angular templates.

Decision. ELK plus my own SVG. ELK's layered algorithm computes node positions and orthogonal edge routes, and everything on screen is markup I control. That is what makes the rest possible: service nodes act as toggle buttons with aria-pressed, focus and selection have separate visuals, and the export serializes exactly what is drawn. D3 would have given the same control, but it changes the DOM directly, next to Angular instead of through it.

Cost. More code: node shapes, edge paths, zoom wiring and export are all my own. For a product under deadline, ngx-graph would have been the reasonable choice. For a learning project, building these parts was part of the point.

Problem. Half-typed YAML is invalid most of the time. If the graph simply followed the latest result, it would disappear on almost every keystroke.

Options. Clear the graph on every error; keep one state object that mixes the last graph with the current errors; or keep the pipeline result honest and add the memory as a separate step.

Decision. The third. state only ever describes the current input: empty, pending, error or ready. A linkedSignal on top derives displayed, which holds on to the last ready result while the input is broken and resets when the editor is emptied on purpose. The pipeline can be tested without any history, and the memory is one named step instead of a rule spread across the app.

Cost. linkedSignal computes lazily: it only remembers a value if something read it while that value was current. The graph view does that on every change, and a comment in the code says so, but it is a dependency on how the signal is used, not only on what it computes.

Problem. ELK needs the size of every node before it can place anything, but the size depends on text: the service name, the image, the port chips.

Options. Render the nodes, measure them and run the layout a second time; measure the text on a hidden canvas; or calculate the sizes from the text.

Decision. Calculated, in a pure function. Images and ports use JetBrains Mono, where every character is exactly 0.6 em wide, so their widths are exact. Names use the proportional Inter, so the estimate there is deliberately generous. The same geometry module tells ELK how large a node is and tells the shape components where to draw its parts, so layout and drawing cannot drift apart.

Cost. Inter widths are an estimate, so some names get a little more room than they need. Text that is too long is shortened, and the full text appears as a tooltip.

Plan. The original design ran ELK in a Web Worker, so that layout would never block the main thread.

Decision. Not in v1. The bundled ELK build already offers an asynchronous API, so the Layout service returns a promise either way, and a real worker later only changes the inside of that service. Getting ELK's worker file through Angular's esbuild-based build, on the other hand, would have added risk to the production build for a benefit that only shows with large files.

Measured. A layout run takes about 10 ms for the example file with 5 services and about 36 ms for 20 services, and it only starts after a 300 ms pause in typing. At 50 services it takes about a quarter of a second, long enough for the next keystroke to lag, and at 100 services more than a second. (Median of 30 runs with Node on my machine, which uses the same V8 engine as Chrome; synthetic compose files.)

Cost. Large compose files make the editor feel sluggish until the worker arrives. It is the first item for v1.1, and these numbers are the baseline it will be measured against.

Accessibility

A graph is visual by nature, so StackGraph does not rely on the picture alone. Everything the graph shows can also be reached with a keyboard and read by a screen reader.

While nothing is selected, the side panel shows a stack overview: every service with its image and ports, every network and volume with the services that use it. Each service there is a button that selects it, so the whole stack can be explored without touching the canvas. Service nodes are focusable toggle buttons with aria-pressed and a name made of service and image. Enter or Space selects a node, Escape clears the selection. Edges are hidden from screen readers, because the detail panel lists the same relationships as text, in both directions. Zoom has its own buttons, so it does not depend on a mouse wheel or a pinch gesture. Selection is a tinted fill with a soft glow; keyboard focus is a neutral ring that only appears for keyboard users. A node can be focused without being selected and the other way round. When a button in the panel replaces the panel's content, focus moves to the new heading instead of disappearing with the button. Only the parse result ("Valid YAML", "2 errors", "Updating…") is a live region. Cursor position and parse time sit next to it, not inside it; otherwise a screen reader would announce every arrow key. The "Show graph" button is never disabled, because a disabled button cannot say why. A click on it explains what is missing instead. Every node type has its own shape and every edge type its own line style, so the graph still reads in grayscale. The color tokens come from a contrast review against WCAG AA in both themes, and animations stop when the system asks for reduced motion.

Not done yet. Networks and volumes cannot be selected in the graph, only read in the overview, and the graph does not yet pan to a service chosen in the panel. There has been no formal audit and no test with a screen reader yet; keyboard behavior and ARIA states are covered by the unit tests.

Lessons learned

Three things that went wrong while building StackGraph, and what each one changed in how I work.

A failed layout that silenced the editor

Every edit runs through a switchMap that parses and lays out the new text. In an early version, a single rejected layout promise travelled up into the outer stream, and in RxJS an error ends the stream it reaches. After that, the editor no longer updated the graph: no error message, no crash, just nothing. The fix was to catch errors inside the switchMap, so a failure ends only that one run and becomes an error state the UI can show. Since then I ask of every operator chain: which stream does this error end?

A test that passed for the wrong reason

displayed keeps the last valid graph with a linkedSignal, and a test checked that clearing the editor removes the graph. It passed, and it would also have passed if the rule had been broken. linkedSignal computes lazily, and the test had never read it while the graph was valid, so there was no previous graph to keep in the first place. The test now first asserts that the graph is visible, and only then clears the input. The same insight shaped the code: the status bar's settled signal is built from the stream instead of a linkedSignal, so it cannot depend on being read at the right moment. A test I have never seen fail tells me very little.

Waiting for time instead of waiting for a state

The state tests originally waited a fixed 400 ms for the pipeline to settle. Locally that was plenty. On the CI runner, the first ELK layout after a cold start sometimes took longer, and tests failed at random. A bigger number would only have moved the problem. Now every wait polls for the condition it actually needs, such as "the state is ready", and a generous timeout is the only fixed number left. A slow machine makes the tests slower, not red.

What's next

v1.1 picks up what the first version deliberately left out. The Web Worker comes first; the rest is grouped by what it improves.

Faster layouts for large files. ELK moves into a real Web Worker, so typing stays smooth beyond 50 services. The measurements in the decisions above are the baseline it has to beat.

Reading large stacks. Toggles in the legend to hide ports, networks or volumes; networks and volumes that can be selected like services; and a graph that pans to whatever is chosen in the side panel, animated only when the system allows motion.

Better error positions. Structural errors get a line number and "Go to line" as well. That needs a YAML parser that keeps source positions for every node, which js-yaml does not.

Getting files in and out. Opening a compose file from disk (read in the browser, never uploaded), PNG export, fonts embedded in the exported SVG so it looks the same on every machine, and shareable links that carry the compose file in the URL itself.

A richer editor. Syntax highlighting and a highlighted current line. That most likely means CodeMirror as a new dependency, so it has to earn its weight first.

What stays out: a backend. Every item above works without a server, shareable links included.

The full list lives in the v1.1 milestone on GitHub.
