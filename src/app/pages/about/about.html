Why I built it

StackGraph is three things at once: a portfolio project, a learning project, and a tool I wanted for myself.

After finishing my training at the Developer Akademie, I wanted a project that is entirely my own, not a course assignment and not a tutorial clone. I use Docker Compose a lot in my own setups, and I kept running into the same problem: the longer a compose file gets, the harder it is to see what is going on. Which service depends on the database, which ones share a network, where data is persisted. The answers are all in the file, but spread across dozens of indented lines. A graph shows them at a glance, and that became the idea for StackGraph.

The learning side was just as deliberate. "Parser" was a word I had used many times without really knowing what it involves, so I wanted to find out by building the part that matters here myself. js-yaml reads the YAML syntax. Everything after that is my own code: turning an untyped tree into a validated, typed model, and turning every problem into an error message a person can act on. It was also the first time I designed an architecture before writing feature code, instead of letting the structure grow as I went. The rest of this page is about the decisions that came out of that.

Goals & constraints

Five requirements shaped almost every technical decision in StackGraph, and each of them ruled something out.

Nothing leaves the browser

Compose files often contain internal hostnames, registry paths and sometimes credentials in environment variables. StackGraph therefore has no backend, no upload and no analytics, and even the fonts are self-hosted so that no request goes to a third party. Parsing, layout and rendering all run on the user's machine, which means every dependency has to justify its weight in the bundle.

Feedback while typing

The graph follows the editor without a render button. Half-typed YAML is invalid more often than it is valid, so the graph must not vanish on every keystroke, and a slow layout run must never overwrite the result of a newer one.

Errors a person can act on

"Invalid YAML" does not help in an 80-line file. Every error names its cause, gives the line and column or the path in the file, and for common mistakes a hint on how to fix it.

A layout that shows direction

Dependencies in a compose file usually form layers, from the proxy down to the database. The layout has to make that order visible, and the result has to leave the app as a clean SVG file. That ruled out force-directed layouts, which are good at clusters but say nothing about direction. It also meant owning the SVG markup instead of handing it to a graph library.

Accessibility is part of v1

A graph is visual by nature, so everything it shows also needs a route that works with a keyboard and a screen reader, and no information may depend on color alone.

Just as deliberate is what v1 leaves out. File upload, drag and drop and PNG export are planned, but none of them was needed to prove the core idea.

How it works

Every edit runs through the same short pipeline: wait for a pause, parse, lay out, draw. Each step hands a typed result to the next.

  1. 01

    Wait for a pause

    The editor writes into a single signal. StackGraph waits until typing has paused for 300 ms before doing any work, and each new keystroke drops whatever is still pending. A layout that finishes late is simply ignored, so it can never replace a newer one.

  2. 02

    Parse into a typed model

    js-yaml turns the text into a plain JavaScript tree. parseCompose then checks that tree and converts it into a ComposeModel. Short and long notations end up in one shape, so "8080:80" and "443" both become port mappings, and structural problems are collected across the whole file instead of stopping at the first one. The result is either a valid model or a list of errors, never something in between. The idea behind this is known as "parse, don't validate".

  3. 03

    Compute the layout

    A pure function translates the model into the graph format of ELK, the Eclipse Layout Kernel. Services, networks and volumes become typed nodes; depends_on, network membership and volume use become three kinds of edges. Node sizes are calculated from their content before the layout runs, because ELK needs them to place anything. ELK's layered algorithm then arranges the graph top-down, so dependencies always point downwards. ELK is loaded only on first use and is not part of the initial download.

  4. 04

    Draw the graph

    Angular binds the positioned nodes and edges directly to SVG elements in a template, with no graph library between the data and the markup. d3-zoom only computes the pan and zoom transform; Angular applies it. Because the SVG on screen is StackGraph's own markup, exporting it means serializing exactly what is drawn, including its computed styles.

  5. 05

    Keep the last good graph

    While the input is invalid, the graph keeps showing the last valid state and the status bar explains what is wrong. An empty editor is treated differently: deleting everything is an intent, not an error, so the graph is cleared. If an update takes longer than 400 ms, a small "Updating…" indicator appears; shorter ones finish unnoticed.

Architecture

Four layers, and dependencies only point downwards. The core of StackGraph does not know that Angular components exist.

Model. At the bottom are plain TypeScript types: the ComposeModel the parser produces and the PositionedGraph the layout returns. compose.model.ts imports nothing at all. Every other part of the app agrees on these shapes, which makes them the real contract between the layers.

Pipeline. Above the model sit the steps described in How it works. Most of them are pure functions without Angular: parseCompose, the mapping to ELK, the node geometry, the reverse lookups behind "required by" and "used by", port formatting and error hints. Angular appears only where a browser or library API requires it. The Layout service wraps ELK's asynchronous API and its lazy loading, and the SVG export needs the DOM.

State. ComposeState is the only place that connects parser and layout. It owns everything that has to do with time: the pause before parsing, discarding outdated results, keeping the last valid graph. Components read its signals and never call the parser or the layout themselves.

Components. At the top, a single container, GraphPage, reads the state and holds the selection. Apart from Home and the editor, which write the text, the graph components receive their data through inputs and report back through outputs. The renderer only knows the PositionedGraph; the detail panel and the stack overview only know the ComposeModel. GraphPage connects the two through the service name. The graph and its text alternative are therefore two independent views of the same model, and neither is derived from the other.

What this buys. The parser, the mapping and the geometry are tested as plain functions, without a component or a DOM. Moving the layout into a Web Worker later only changes the inside of the Layout service, because its contract is a promise that stays the same. And the node geometry is defined once and used twice: the mapping uses it to tell ELK how large a node is, the shape components use it to draw that node. A node is always drawn exactly as large as ELK planned it.

What it costs. The positioned graph extends ELK's own types, and the renderer reads edge routes in ELK's format. Replacing ELK with another layout engine would therefore mean touching the renderer too. A neutral graph type would remove that coupling, but with a single layout engine it would add a translation step that nothing currently needs.
